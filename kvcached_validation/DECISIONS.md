## D2. How LMCache MP reaches vLLM's KV memory (read before Experiment B)

**Facts:** In MP mode the default `lmcache_driven` transfer has the LMCache *server process* read/write vLLM's GPU KV blocks directly through CUDA IPC memory handles (`lmcache/v1/platform/devices/cuda/ipc_wrapper.py`). kvcached allocates KV through the CUDA VMM API (`cuMemCreate`/`cuMemMap`, `csrc/inc/gpu_vmm.hpp`) with `requestedHandleTypes` left at 0, i.e. *not exportable*. LMCache has a `lmcache.mp.use_vmm_api` switch (VMM IPC) but it requires exportable allocations and one physical chunk per tensor; kvcached backs one tensor with many 2 MiB pages. LMCache also has an `engine_driven` transfer mode where the vLLM worker itself gathers/scatters KV (no cross-process GPU handle).

**Predictions for Experiment B:**
- B1 `lmcache_driven` (default): fails at `register_kv_caches` with a CUDA IPC error (invalid argument on a VMM pointer).
- B2 `lmcache_driven` + `use_vmm_api`: fails at registration, "allocation not exportable" or "multi-chunk".
- B3 `engine_driven`: registration succeeds; serving works; the open question is whether a shrink while a load/store copy is in flight faults (kvcached pins pages only for vLLM's native `OffloadingConnector`, see `offload_pins.py`).

**Outcome:** _pending_

## D4. Tooling rehearsal (15:21–15:23) and Experiment A1 design

**Rehearsal result (1 req/s, 6k-token prompts, limit 12.78 G → 4 G → 12 G):** everything measured as intended. kvcached maps pages on demand: at idle it holds 64 MiB; each 6k-token request adds 0.75 GiB and the pages are unmapped (NVML drops) within one sample of the request finishing. `kvctl limit` is a Python process that takes ~1.5 s to run; the new limit shows up in the shared segment just before it exits, so the analysis uses the instant the sampler first sees the new limit as t = 0 (kvctl's return time as fallback). At 1 req/s the 4 GiB limit was never binding (peak use 3.75 GiB), so nothing was blocked. ITL p99 ≈ 0.46 s / max 0.9 s comes from 6k-token chunked prefills sharing steps with decodes (plain vLLM behaviour, to be confirmed in the overhead comparison).

**A1 design:** 3.5 req/s Poisson, 6000-token prompts, 128 greedy output tokens, 150 s; limit 12.78 G (startup) → **3 G at t=40 s** → **12 G at t=90 s**. With ~10–14 requests resident (7.5–10 GiB) the 3 GiB limit is binding (≈ four 6k-token requests).

**Prediction:** no request fails and no vLLM preemption is counted: kvcached stops backing *new* pages beyond the limit, so already-running requests keep decoding and new admissions wait; mapped memory falls as the resident requests finish, so it reaches the 3 GiB plateau within roughly one request lifetime (≈ 4–6 s) and ITL during the shrink is unchanged or lower; the waiting queue then grows (TTFT rises) until the 12 G command, after which the backlog drains within ~10–20 s. Memory re-acquisition after the grow is as fast as admissions (sub-second per request).

**A1 outcome (15:24–15:28, `results/expA1*`):** 480/480 requests completed, 0 errors, vLLM preemption counter stayed at 0. The new limit is visible in the segment 1.25 s after `kvctl` is invoked (Python start-up of the CLI; the engine's watcher polls every 100 ms). Engine log at the shrink: `shrink to 1536 blocks refused by allocator (in-use pages above target); keeping shrink pending` — kvcached does not revoke pages in use. Running requests 15 → 7 after 1 s → 3–4 after 3 s as they finished; NVML 29.66 → 20.66 GiB (kvcached 11.9 → 3.0 GiB) reached within 2.7 s of the limit becoming visible. Afterwards exactly 4 requests (4 × 0.75 GiB = 3 GiB) ran at a time; ITL median fell 19.6 → 12.8 ms (smaller batches); the queue grew. Grow: memory 3.0 → 11.9 GiB in 6.2 s, limited by how fast new 6k-token prefills are admitted (~1.5 GiB/s). **Caveat:** 3.5 req/s × 6000 tokens exceeds this GPU's prefill throughput (~9.6k tok/s), so the queue was already 55 deep before the shrink; TTFTs are meaningless as SLO numbers. Prediction held on every mechanism point; the load level was mis-chosen.

**A1b design/prediction:** same, at 1.2 req/s (≈7k prompt tok/s, under capacity) with a 2 GiB limit (≈ two 6k-token requests). Expect a stable baseline of 5–8 running requests and an empty queue, then the same shrink dynamics with release complete within ~3 s, a queue forming only while the 2 GiB limit holds, and a drain after the grow.

**A1b outcome (15:31, `results/expA1b*`):** 160/160 ok, 0 preemptions, but at 1.2 req/s with 128-token outputs only 2–3 requests are ever resident (0.75–2.25 GiB), so the 2 GiB limit barely bound and there was nothing to release. The sampler/loadgen also revealed that vLLM delivers several tokens per SSE chunk under load (A1: 480 requests × 128 tokens but only ~90 chunks/request), so chunk gaps over-state per-step time; `loadgen.py` now requests `return_token_ids` and `analyze.py` divides each gap by the tokens in the chunk. (Procedural slip: editing `run_resize_exp.sh` while A1b was still running broke its last line, because bash reads scripts incrementally; the data files were complete and were analysed by hand. Rule from here: never edit a runner while a run is active.)

**A2 design/prediction (15:34):** 1.2 req/s, 6000-token prompts, **512** output tokens (≈8 s residency → ~10 resident requests ≈ 8 GiB, prefill 7.2k tok/s under the ~9.6k tok/s capacity), limit 12 G → 3 G at 40 s → 12 G at 90 s. Prediction: steady ~8 GiB before the shrink; after the shrink the resident set drains to ≤ 3 GiB within one residency (~8 s) with no kill/preempt; admissions then run ~3–4 at a time and a queue builds; after the grow the queue drains in ~20–30 s.

**A2 outcome (15:35–15:39, `results/expA2*`):** 160/160 requests completed with all 512 tokens, 0 errors. Baseline before the shrink was heavier than predicted (15 running, 11.5 GiB, i.e. at the 12 GiB capacity — 512-token outputs make residency ~10 s, not 8). Shrink 12 G → 3 G: no running request was stopped at the shrink; mapped memory fell 11.5 → 4.1 GiB in 8 s and fitted under 3 GiB after ~22 s as the 15 resident requests ran to completion (pages in use are never revoked; engine log repeats "shrink … refused by allocator (in-use pages above target); keeping shrink pending"). **New finding:** the vLLM preemption counter went 0 → 15. The stalls start 19.6 s *after* the shrink and continue after the grow: once the resident set sits at the cap (3 GiB, or the 12 GiB capacity with 15–16 running), decoding requests that need one more block are preempted and later recomputed — vLLM's ordinary behaviour at a full KV cache, now triggered by the kvcached limit, which shrinks vLLM's logical block count (1536 blocks). kvcached's own "pool exhausted" path was never hit (0 warnings). Longest stall 7.0 s (a preempted request waiting to be re-prefilled). Grow 3 G → 12 G: memory re-acquired 2.4 → 11.9 GiB in 5.4 s, bounded by prefill admission; the queue (28 waiting) then drained over ~30 s. Prediction was right on release (no kill, drain by completion) and wrong on "no preemption": preemption does happen, but as cap-pressure preemption with recompute, not at the shrink instant.

## D5. Per-step overhead comparison (15:40)

Design: same engine class, static 8 GiB KV budget — kvcached engine with `kvctl limit vllm_a 8G` vs a fresh plain engine with `--kv-cache-memory-bytes 8G` (both Model Runner V2, same flags) — under 1.0 req/s × 6000-token prompts × 256 output tokens for 120 s (≈ 4–5 resident requests, ≈ 3.5 GiB, so the budget never binds). Metrics: per-token ITL p50/p90 (decode step time), TTFT p50, throughput. Prediction: kvcached adds < 5 % to the median step time (its per-step work is page bookkeeping on the scheduler side, not in the kernels); TTFT equal within noise.

**D5 outcome (15:40–15:47, `results/expOH_*`, `results/overhead_comparison.md`):** per-token step time is identical within measurement noise: decode-only step p50 14.03 ms vs 14.03 ms, p90 16.17 vs 16.18 ms, ITL p99 457.9 vs 457.6 ms (prefill-sharing steps), TTFT p50 0.49 s both, same wall-clock span for the same 100 requests. Greedy outputs of 8 fixed prompts are byte-identical between the plain and the kvcached engine. Prediction (< 5 %) held with margin: no measurable per-step overhead at a static budget.

## D6. Experiment B1 — LMCache MP connector, default `lmcache_driven` transfer (15:47–15:48)

(Side issue first: port 5555 is held by an unrelated listener on this machine, so the LMCache server is on 5556; the first B1 attempt had an engine with no server and was discarded.)

**Outcome: fails at KV registration, exactly as predicted in D2.** The engine comes up through kvcached's allocation (same "MRV2 persistent allocation" line as in A), the connector loads from `lmcache.integration.vllm.lmcache_mp_connector`, creates its transfer context with `mode=lmcache_driven`, then `CudaIPCWrapper.__init__` calls `tensor.untyped_storage()._share_cuda_()` (PyTorch storage IPC = `cudaIpcGetMemHandle`) on the first KV tensor and PyTorch raises `RuntimeError: invalid device pointer: 0x1f0000000000` — a kvcached VMM-reserved virtual address that legacy CUDA IPC cannot export. EngineCore exits; kvcached's teardown then logs `mem_unmap during FTensor cleanup failed: unknown CUDA driver error` (secondary, the context is already gone). Full excerpt: `results/expB_lmcache_driven_kvcached_failure.txt`. No request was ever served; nothing to measure.

**B2 prediction (`lmcache.mp.use_vmm_api=true`, still lmcache_driven):** `VmmCudaIPCWrapper` reads the allocation's `requestedHandleTypes`; kvcached creates its pages with `cuMemCreate(..., flags=0)` and no handle type, so wrap should fail loudly with the "not exportable" message (or, if it gets past that, with the multi-chunk message, since each KV tensor spans many 2 MiB pages).

**B2 outcome (15:49, `results/expB_vmm_kvcached_failure.txt`):** fails at registration one check *earlier* than predicted: `VmmCudaIPCWrapper` first demands a (permutable-to-)contiguous tensor and raises `ValueError: VmmCudaIPCWrapper requires a tensor that is contiguous …; got shape=(6661, 16, 8, 256) stride=(1048576, 2048, 256, 1)`. kvcached's default contiguous layout (BLNHC) interleaves all 32 layers inside each block, so each per-layer view has a block stride 32× its dense size. The exportability check was never reached.

**B2b (same, with `KVCACHED_CONTIGUOUS_LAYOUT=false`, one pool per layer):** per-layer tensors become dense, so the wrapper should get past the contiguity check and then fail on exportability (kvcached's `cuMemCreate` requests no shareable handle type) or on the multi-chunk rule. Prediction: still fails at registration; the exact message tells which.

**B2b outcome (15:50, `results/expB_vmm_kvcached_lbnhc_failure.txt`):** as predicted. With the per-layer layout (`layout=LBNHC`) the contiguity check passes and `VmmCudaIPCWrapper` then raises `RuntimeError: cannot export VMM allocation (requestedHandleTypes=0): the VMM allocation was created without an exportable handle type (… neither POSIX_FILE_DESCRIPTOR nor FABRIC). Exportability is fixed at cuMemCreate time and cannot be added later.` kvcached's `cuMemCreate` (csrc/inc/gpu_vmm.hpp, `prop.requestedHandleTypes` unset) makes its pages non-exportable, so no server-side (lmcache_driven) zero-copy path can reach them without a kvcached patch; and even with POSIX-fd exports, LMCache maps one handle per tensor whereas kvcached backs a tensor with many physical pages (the multi-chunk rule), so a patch would be non-trivial.

## D7. Experiment B3 — `engine_driven` transfer (worker-side gather/scatter), kvcached default layout (15:51)

Prediction (from D2): registration succeeds (no cross-process GPU handle is needed: the vLLM worker copies KV between its own GPU tensors and pinned/inline buffers; the LMCache server only sees host memory). Serving then works; stores are asynchronous (background thread, copy stream), retrieves are synchronous on the worker. The shrink/grow under the session workload should behave as in A because copies happen inside the engine process while the pages are still mapped; the risk is a store copy that is still in flight for a *finished* request when kvcached unmaps its pages (kvcached pins pages only for vLLM's native OffloadingConnector).

**B3 outcome (15:51–15:56, `results/expB_engine_driven_kvcached*`):** registration succeeds ("Worker engine-driven context registered (… mode=pickle)") and the engine serves. Session load (6 sessions, 3000-token contexts growing by 256 tokens per turn, prefix caching off so every turn's prefix is fetched from LMCache): 91/91 requests ok, 0 errors, 0 vLLM preemptions, 0 kvcached warnings, LMCache server 89 stores / 84 retrieves (379,648 tokens served from L1), 0 error lines on either side, across a 2 G shrink and a 12 G grow. So the combination *runs* in this mode. Two qualifications: (1) the transfer path is slow — retrieves run at ~5.4k tok/s (0.75–1.2 s per 4–6k-token prefix) and stores at ~0.9k tok/s because the inline "pickle" transport ships tensors over ZMQ; retrieves are synchronous on the worker, so every other running request's decode stalls for that time (74 stalls > 1 s across 42 requests; TTFT p50 2.6 s). (2) **greedy outputs differ from the plain engine on 4 of 8 fixed prompts** (deterministic across three repeats on this engine; kvcached alone matched plain 8/8). Whether (1) and (2) are LMCache's doing or kvcached's needs the plain-engine control with the same connector, running now.

**Control outcome (16:00–16:05, `results/expB_engine_driven_plain*`):** plain engine + the same connector reproduces B3's behaviour without kvcached: 97/97 ok, 96 stores / 91 retrieves, retrieves 5.9k tok/s, stores 0.76k tok/s, TTFT p50 2.5 s, 55 stalls > 1 s — the slow transport and the stalls are LMCache's inline transfer, not kvcached. Greedy outputs: plain+connector = kvcached+connector on 8/8 prompts, and both differ from the no-connector engines on the same 4/8 prompts, so the output change is introduced by the LMCache MP connector itself (independent of kvcached; `results/output_check_comparison.md`). (Runner bug found and fixed: `run_resize_exp.sh` deleted `<name>_*.jsonl`, which wiped the check files written just before it; the checks were redone by hand against the still-running engines.)

**Stress variant (16:06):** kvcached + connector, 6 sessions with 6000-token first turns growing by 512 per turn, think 2 s, shrink/grow every 15 s (2G/12G alternating ×3). Purpose: large stores (0.75 GiB of KV gathered GPU→host per finished request) overlapping frequent unmaps. Prediction: no crash, because the connector returns `_can_store=True` from `request_finished`, so vLLM keeps the blocks until `get_finished` reports the store done and kvcached can only unmap pages after that; expect stalls and preemption-free completion as before.

**Stress outcome (16:03–16:06, `results/expB_engine_driven_kvcached_stress*`, crash evidence in `..._stress_crash.txt`): the prediction was wrong — the engine crashed.** 79 of 84 requests completed (the six shrink/grow steps all took effect; kvcached logged one "pool exhausted → scheduling miss" and two `available_size()=7 < need_size=39` warnings at the 2 G cap, no preemption counted). At t = 148.4 s (16:06:29, 43 s after the last grow, limit 12 G, 3 requests running, KV 26 % used) LMCache's background store thread raised `torch.AcceleratorError: CUDA error: an illegal memory access was encountered` in `async_engine_driven.py:310 gather_done.synchronize()` ("Async engine-driven store failed for request_id=cmpl-947b…", the request whose 5632-token prefix had just been retrieved and prefilled); the sticky CUDA error then failed the next retrieve's scatter and EngineCore died, taking the 5 in-flight requests with it (HTTP 200 streams ending in an error object). The kernel log has the primary evidence: `NVRM: Xid 31, pid=144264 (VLLM::EngineCore) … MMU Fault … faulted @ 0x1f00_0a4dc000. Fault is of type FAULT_PDE ACCESS_TYPE_VIRT_READ` — a *read* of a virtual address inside kvcached's VMM reservation (the same `0x1f00…` range B1 reported) that had **no physical page mapped**. So LMCache's asynchronous GPU→host gather, which runs on its own CUDA stream and is not covered by kvcached's physical-release ordering (kvcached pins pages only for vLLM's native OffloadingConnector), read a kvcached page that was unmapped. Not determined here: whether the page had been unmapped by kvcached's normal reclaim of freed blocks or by the limit changes, and whether LMCache's block-id list reached beyond the blocks vLLM had allocated (a plain pool would return garbage silently; kvcached faults). The no-resize repeat (next) separates "needs a shrink" from "happens anyway". Nothing in the LMCache server log; the server stayed up.

**No-resize repeat outcome (16:08–16:13, `results/expB_engine_driven_kvcached_stress_noresize*`, `..._crash.txt`): reproduces without any limit change.** Same load, limit left at its start-up value (13 G), 0 kvcached warnings: after ~90 s the identical failure — `Async engine-driven store failed … CUDA error: an illegal memory access` in LMCache's background gather, kernel `Xid 31 … FAULT_PDE ACCESS_TYPE_VIRT_READ` inside the kvcached range — killed EngineCore (52 requests had completed; the load generator's remaining 132 requests then failed against the dead engine). So the fault is not caused by resizing: kvcached + LMCache MP `engine_driven` crashes under ordinary store traffic once stores are large (≈2–3k tokens per store here vs 256 in B3). The B3/control pair with 256-token stores survived 150 s twice; that is luck of the race, not safety. Plain engine + the same connector and load is being run as the final control.

**Final control outcome (16:14–16:19, `results/expB_engine_driven_plain_stress*`):** plain engine + connector under the identical stress load: 94/94 ok, 0 errors, engine healthy afterwards, no Xid. The crash needs kvcached. Conclusion for B: `lmcache_driven`/VMM modes cannot register; `engine_driven` registers but faults under store traffic independent of resizing. Engines stopped; results committed.

## D8. Live shrink sweep at fixed RPS with DRAM offload (re-doing the vram-limit study 1 with kvcached) — 16:30

**Reference:** `branches/vram-limit/reports/report_simple_inference.md` (study 1): Llama-3-8B, 32 sessions × 6144-token prefixes (24 GiB of KV demand), each request = prefix + 128 unique tokens → 128 output tokens, Poisson 2 QPS, Zipf-1.1 or uniform session choice, 32-request warm-up, vLLM *native* CPU offload (`--kv-offloading-backend native`) with a 24 GiB pinned DRAM tier. There the GPU KV budget was changed by **restarting** the engine with a different `--gpu-memory-utilization` (13.77 → 1.77 GiB of GPU KV): TTFT flat (p50 54 → 73 ms, p95 305 → 332 ms, 0 preemptions) down to 5.77 GiB, then collapse at 3.77 GiB (p95 1.5 s, preemptions) and a stall at 1.77 GiB; the wall is in-flight KV (Poisson p95 of 7 in flight × 0.77 GiB ≈ 5.4 GiB), not cache capacity.

**New design:** same workload, same offload backend, but the GPU KV budget is **shrunk live with kvcached** in one continuous run: baseline at the start-up limit for 60 s, then `kvctl limit` 10G → 8G → 6G → 5G → 4G → 3G → 2G, 60 s (≈120 requests) each, 2 QPS throughout. Per-window metrics: TTFT p50/p95, per-token ITL, tok/s, preemptions, GPU prefix hit rate and DRAM (external) hit rate from vLLM's counters. Control: the same sweep without offload (prefix caching only), where evicted prefixes must be recomputed (~0.5 s of prefill at 6k tokens).

**Why kvcached main instead of 0.1.6:** 0.1.6 has no handling of vLLM's OffloadingConnector, and the LMCache result above shows what an un-pinned asynchronous copy does to VMM pages. kvcached main (`9106e0f`, 2026-11-04) pins the pages of every offload copy job until the workers report it complete (`offload_pins.py`, vLLM 0.29–0.30, Model Runner V2) and releases the prefix cache when the limit is lowered (#552). Built into `.venv-main` (`scripts/setup_env_main.sh`), everything else identical.

**Prediction:** with offload, TTFT/ITL/tok/s stay within ~10 % of the baseline down to the 5–6 GiB windows while the GPU hit rate falls and the DRAM hit rate rises to make up for it; 0 preemptions until the resident set no longer fits (4 GiB window: a few preemptions, p95 TTFT up several ×; 3 GiB and 2 GiB: heavy preemption, possibly waiting-queue growth). The transition at each shrink costs nothing visible beyond the first few seconds (prefix-cache eviction + unmap). Without offload, the knee comes earlier: every lost GPU hit costs a ~0.5 s recompute, so TTFT p50 rises as soon as the hot set (Zipf: 17 sessions ≈ 12.75 GiB) exceeds the budget — i.e. already in the 10G/8G windows.

**D8 first run outcome (17:03–17:12, `results/sweep_offload_zipf*`):** the mechanism result is clean, the baseline is not what study 1 had. Across 13 G (start) → 10 → 8 → 6 → 5 → 4 G: TTFT p50 138–156 ms, p95 350–790 ms, ITL p50 12.7–13.2 ms, 244–277 tok/s, **0 preemptions, 0 stalls, 0 failures** — flat, as predicted. At 3 G: TTFT p50 3.2 s (p95 5.9 s), waiting up to 13; at 2 G: TTFT p50 18 s, waiting 34; still 0 preemptions and ITL even lower — kvcached turns the shortage into admission queueing, not into the preempt/recompute spiral study 1 saw with a static budget. **But** kvcached's own prefix-cache bound kept "kvcached used" at 4.31 GiB from the very first window (GPU prefix hit 30–42 %, DRAM hit ~90 % already at 13 G), so the 13 G/10 G/8 G/6 G windows are all effectively the same ~4 GiB configuration, and the baseline TTFT (147 ms) is the DRAM-fetch TTFT, not study 1's 54 ms at 13.77 GiB of GPU KV. Cause: `KVCACHED_MAX_CACHED_BLOCKS` / `KVCACHED_MAX_CACHED_TOKENS` defaults (1000 blocks / 16 000 tokens ≈ 2 GiB of cached prefixes). Rerun with the cache bound raised to the whole budget so that the sweep actually starts from a full GPU cache.

**D8 second run outcome (17:15–17:25, `results/sweep_offload_zipf_full*`, `KVCACHED_MAX_CACHED_TOKENS=-1`):** now the baseline matches study 1 (GPU prefix cache fills the budget: kvcached used 12.3 GiB, GPU hit 76 %, TTFT p50 51 ms vs study 1's 54 ms). Each `kvctl limit` evicted cached prefixes down to exactly the new limit (kvcached used = 10.0, 8.0, 6.0, 5.0, 4.0, 3.0, 2.0 GiB) within the window. Performance across 13 → 4 GiB: TTFT p50 51 → 52 → 91 → 72 → 146 → 155 ms as GPU hits fall 76 → 43 % and DRAM hits rise 72 → 95 %; TTFT p95 350–800 ms; ITL p50 12.6–13.1 ms and 244–277 tok/s unchanged; **0 preemptions, 0 stalls, 0 failures in every window**. At 3 GiB TTFT p50 3.2 s (queue 13), at 2 GiB 18 s (queue 34), still 0 preemptions and all requests complete. Compared with study 1's static sweep at the same GPU-KV sizes: 5.77 GiB there 73/332 ms vs 6 GiB here 72/351 ms; 3.77 GiB there 135/1528 ms with preemptions vs 4 GiB here 155/795 ms with none; 2.77 GiB there 2.1/5.5 s + preemptions vs 3 GiB here 3.2/5.8 s, no preemption; 1.77 GiB there an engine stall vs 2 GiB here a deep queue but a healthy engine. Prediction held (flat to the in-flight-KV knee, then queueing rather than a spiral); the one deviation is that the knee shows as admission queueing with zero preemptions, because kvcached refuses to back pages beyond the limit and vLLM's scheduler simply waits. One benign kvcached warning (`alloc_page() failed after partially allocating 296/392 blocks; rolled back`) in the 2 G window. Control without offload running next.

**Control outcome (17:27–17:37, `results/sweep_nooffload_zipf_full*`):** without the DRAM tier the same live sweep degrades from 8 GiB on: TTFT p50 52 → 66 → 505 → 500 → 3 488 → 7 053 ms → 28 s → 90 s (13 → 2 GiB), queue from 5 GiB (18 waiting), a handful of preemptions below 4 GiB; ITL unaffected. ## D9. Decode-only emulation and a static control on the same vLLM (17:50)

**Decode-only emulation (live, kvcached main):** same reference workload (32 × 6144, +128, 128 out, Zipf, 2 QPS), vLLM native offload with a **28 GiB** DRAM tier (holds all 32 prefixes plus suffix blocks, so nothing is ever recomputed) and **prefix caching off**, so the GPU holds only in-flight KV and every request's prefix arrives from the DRAM store — the decode-engine situation of the proposal, with the store standing in for the prefill GPU. Judged, per the vram-limit conventions, on TPOT, scheduler queue wait (`vllm:request_queue_time_seconds`), throughput and failures; TTFT here is fetch + 128-token prefill, not a first-token latency. Limit 13 G → 10 → 8 → 6 → 5 → 4 → 3 → 2 G, 60 s each.

Predictions: (a) native offload still stores/loads with APC off (to be confirmed by the warm-up's external hit counter); (b) from 13 G to 4 G: TPOT p50 ≈ 13 ms flat, queue wait ≈ 0, 255 tok/s offered = delivered, 0 preemptions; at 3 G and 2 G the in-flight wall: queue wait and TPOT grow (requests wait for a KV slot), delivered tok/s falls below offered, still 0 preemptions.

**Static control on the same vLLM 0.30 (plain engine, no kvcached):** one restart per budget with `--kv-cache-memory-bytes` = 13, 10, 8, 6, 5, 4, 3, 2 GiB, 150 s (≈300 requests) each, two arms: (i) study-1 style (APC on, 24 GiB tier) to compare with `sweep_offload_zipf_full`; (ii) decode-only style (APC off, 28 GiB tier) to compare with the emulation above. Prediction: flat regions equal within run-to-run noise (±15 ms TTFT, same TPOT); below the knee the static engine preempts/recomputes (study 1's spiral; vLLM 0.30 may stall less) while the live engine queues.

**D9 decode-only live outcome (17:59–18:12, `results/sweep_decodeonly_offload_zipf*`):** (a) confirmed — native offload stores and loads with prefix caching off (DRAM hit 95–98 % of looked-up tokens in every window; GPU prefix hits n/a). The GPU holds only in-flight KV: kvcached used 3.1 GiB at the 13 G limit. (b) 13 → 6 GiB: TPOT p50 13.2–14.1 ms, scheduler queue wait 111–149 ms mean (that is the prefix fetch itself: the request waits for its KV slot + 0.77 GiB load), delivered = offered, 0 preemptions. 5 G and 4 G: TPOT still 14 ms but queue wait 575–662 ms and TTFT p95 2–2.5 s — the in-flight set (mean ≈ 3.7 requests ≈ 2.9 GiB, p95 ≈ 5.4 GiB) starts to bump the limit (used 3.88 GiB against 4 G). 3 G: queue wait 4.1 s, delivered 1.69 req/s vs 2 offered, 1 preemption; 2 G: queue wait 18 s, 1.22 req/s, e2e p50 34 s, 0 preemptions, 0 failures. So, judged on decode metrics only: decode speed never changes; the budget can go from 13 to 6 GiB with nothing visible, 5–4 GiB adds ~0.5 s of queueing per request, and below 4 GiB the engine is capacity-bound and queues instead of failing. Prediction (b) held except that the queueing onset is one step earlier (5 G, not 3 G) — the p95 of the in-flight set, not its mean, sets it. Static controls (two arms, ~70 min) launched at 18:13.
