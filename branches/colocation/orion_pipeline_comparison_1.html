PyTorch kernel launch: Normal path vs. Orion — with the CUDA / driver / GPU layers

Both stacks start from the same PyTorch op and end at the same silicon. The bands show which software layer each step lives in. The key takeaway: Orion inserts itself above the CUDA Runtime — everything from the CUDA Driver down (user-mode libcuda.so, kernel-mode nvidia.ko, and the GPU's on-chip scheduler) is completely untouched.

How the normal path works

When PyTorch runs an op like a convolution, it calls into cuDNN / cuBLAS, which in turn call the CUDA Runtime function cudaLaunchKernel (step 2). The runtime hands the launch to the CUDA Driver (libcuda.so, step 3), which builds the actual launch command and pushes it onto a GPU stream/channel.

The kernel-mode driver (nvidia.ko, step 4) submits that command buffer to the device over an ioctl, and the GPU's own hardware scheduler (step 5) runs the kernels — for a single application, in stream order. There is no opportunity for an outside policy to reorder or throttle anything: whatever PyTorch submits goes to the GPU immediately.

How Orion intercepts it

1 · Shadow the symbolOrion compiles its wrappers into libinttemp.so and injects it with LD_PRELOAD, so its own cudaLaunchKernel (and cuDNN/cuBLAS entry points) load before the real ones. PyTorch's call by name now lands in Orion's function instead of the CUDA Runtime's — with zero changes to PyTorch.

2 · Identify the callerThe wrapper calls get_idx, which reads the OS thread id (gettid) and looks it up in a shared table to decide which client this launch belongs to — and whether the caller is an application thread or the scheduler itself.

3 · Capture, don't executeFor an application thread, Orion packs every launch argument (function pointer, grid/block dims, args, shared mem, stream) into a func_record and pushes it onto that client's software queue (kqueues) under a mutex. The kernel is not sent to the GPU. The wrapper then calls block and spins until the entry is served, so PyTorch sees ordinary synchronous behavior and gets cudaSuccess back.

4 · Scheduler decidesA separate scheduler thread in the same process shares those queues. It polls them and applies Orion's interference-aware policy — using each kernel's SM footprint and compute-vs-memory profile against SM_THRESHOLD and DUR_THRESHOLD — to decide when a best-effort kernel may run alongside the high-priority job.

5 · Re-issue on a chosen streamschedule_kernel re-issues the captured launch as a real cudaLaunchKernel, but on a stream whose priority Orion picked. Because that call re-enters the same shadowed wrapper, get_idx now recognizes the scheduler thread and takes the passthrough branch straight to the real CUDA Runtime (via a dlsym(RTLD_NEXT) pointer). From there — Driver, kernel driver, GPU — everything is byte-for-byte the normal path.

The layers, top to bottom

  • PyTorch (framework). Identical in both. It calls CUDA functions by name and never knows Orion exists — it just gets a normal cudaSuccess back.
  • Orion (only on the right). libinttemp.so, injected by LD_PRELOAD, defines its own cudaLaunchKernel / cuDNN / cuBLAS symbols that shadow the real ones. This whole band is what Orion adds; it sits between PyTorch and the real CUDA Runtime.
  • Orion scheduler thread. Same process as the app, shares the queues, applies the interference-aware policy, and re-issues each captured launch on a priority-assigned stream. The dotted loop back into the wrapper is the re-entrancy: the scheduler's own call takes the passthrough branch to the real runtime.
  • CUDA Runtime API — libcudart.so (+ cuDNN, cuBLAS). This is the layer Orion intercepts. In both stacks the real runtime functions still run; Orion just controls when and on which stream.
  • CUDA Driver API — libcuda.so (user-mode driver). The runtime calls down into the driver (cuLaunchKernel), which packages the launch and pushes it to a GPU channel. Orion does not touch this layer.
  • Kernel-mode GPU driver — nvidia.ko. Receives the submission via ioctl and places it on the GPU's ring/pushbuffer. Unchanged by Orion.
  • GPU hardware. The on-chip hardware scheduler runs the kernels. Same silicon in both — the only difference is what arrives: one default stream vs. several prioritized streams whose ordering Orion shaped upstream.

Orion operates entirely in user space at the CUDA Runtime boundary. It never replaces or patches the CUDA driver or the kernel module — it just re-issues ordinary cudaLaunchKernel calls, so from the driver's perspective the traffic looks like a normal application using multiple streams.
