N homogeneous LLMs on one GPU: what scales, what breaks

We colocated N identical vLLM engines on a single RTX 5090 under MPS and scaled N until something ran out, for a 0.5B and a 3B model, with KV caches that fit in VRAM and with KV 3× oversubscribed to host DRAM. This page gives the configuration, the measurements, and the mechanisms we could verify.

3.6×TPOT at N=8 for the 0.5B (1.56 → 5.70 ms) at 2 QPS per model; all requests served.
≥ 8×load headroom at N=8: 16 QPS per model, 15.3k tok/s total, zero scheduler queueing.
4 / 4stock-config runs collapsed at N=4 with DRAM-offloaded KV. Cause: CPU thread oversubscription.
~4×TPOT penalty for splitting the same 32 QPS across 8 engines instead of batching in one.

Summary. Under MPS, colocation costs per-token latency, not capacity, provided each engine's CPU thread pool is capped. With stock settings the first failure is on the host: N engines × ~135 threads spin-wait on 32 cores, starve the GPU, and the system collapses. With the cap, the binding resource depends on model size and KV working set: GPU time, host RAM, VRAM, the per-engine sequence cap, or a queue of KV reloads.

Models and per-engine memory budget

Serving cells

2 · Scaling at 2 QPSResident KV: latency rises smoothly, throughput holds

With KV resident, every engine serves its offered load at every N (256 tok/s per model). The cost is per-token time. Decode-only and full cells share one TPOT curve: the 128-token suffix prefill is too small to matter at this rate.

Read SM-active with care. It counts how often SMs are busy, not how full they are. In the capacity sweep (§4) it falls from 0.78 to 0.68 at N=4 while throughput doubles. The knee visible here is a per-token latency knee at 2 QPS, not a capacity limit.

3 · The failureCPU thread oversubscription collapses the system at N=4

With stock settings and offloaded KV, the 0.5B cohort is healthy at N=3 and collapses at N=4 in four of four runs: 489–619 of 1,200 requests time out (300 s), aggregate throughput falls to 158–192 tok/s (15–18% of offered), and GPU1 sits at 0.03–0.05 SM-active while host CPU is 93–97% busy.

Mechanism, measured at the thread level

Each uncapped EngineCore runs ~135 threads; its torch/OpenMP pool is sized for the whole machine. Stack sampling was not possible (no ptrace, perf or sudo), so we sampled /proc/<pid>/task/* for every EngineCore every 2 s during a fourth stock reproduction.

Controls

Rule. Cap each engine's CPU thread pool at or below cores ÷ N. vLLM and torch default to one engine per machine. The cap removed the failure in every run and was neutral everywhere else.

4 · CapacityLoad sweeps at fixed N

At 2 QPS every resident cell keeps up, which hides how much headroom is left. We swept the per-model rate at fixed N (decode-only · fits, thread cap on). A point keeps up if the engines' mean scheduler queue wait is under 50 ms and at most 1% of requests fail.

Why not delivered/offered. Each client sends a fixed 300 requests. At 16 QPS they arrive in ~19 s and the window then waits ~1.5 s for the last completion, so delivered/offered reads 92–94% with zero queueing. Queue wait from vllm:request_queue_time_seconds does not have this bias. The short windows also mean these points show no queueing over 10–20 s, not sustained stability.

A configuration trade-off. Lowering max-num-seqs from 64 to 16 is what raised the 3B's KV grant from 0.59 to 0.94 GiB (§1). It cut N=1 decode-only offload first-token wait from 742 to 103 ms, and it is also what bounds each engine's capacity here. The GPU-bound capacity of the 3B was not measured.

The cost of N at equal total load

5 · Offloaded KVSmall models are unaffected; the 3B queues on reloads

Qwen2.5-3B: queueing grows with N

  • N ≤ 3: the KV grant bounds concurrency. Each in-flight request holds a full prefix, so ~4.4 fit. Little's law gives the concurrency needed, 2 QPS × (load + 128 × TPOT) = 2.1 at N=1 and 3.8 at N=3, matching the 2.0 and 3.8 requests observed running, with KV use rising to 71%. Neighbours stretch TPOT, each request holds its slot longer, and the same grant serves fewer requests per second.
  • N = 4: the reload itself is the bottleneck. 13.6 requests wait while 2.1 run and KV is 43% used. The mean KV load is 401 ms against 85 ms at N=1. The thread-cap dose-response (§3) shows this is not thread starvation. Which shared resource the reloads queue on (copy engines, kernels under MPS, PCIe) is not separated by these runs.
  • Full · offload degrades later (TTFT 74 → 148 ms to N=3, 621 ms at N=4). The full cells use zipf sessions and the decode-only cells uniform ones, so the gap between them is confounded by skew; we did not run the decode-only + zipf control.

6 · SynthesisWhat binds first

Practical guidance

  1. Set OMP_NUM_THREADS ≤ cores ÷ N for every engine. Values of 2, 4 and 8 behaved identically at N=4.
  2. Run under MPS.
  3. Budget latency, not capacity. 3.6× TPOT at N=8 for 0.5B, 2.55× at N=4 for 3B, at 2 QPS per model.
  4. Colocate for isolation, not efficiency. One engine batching the same traffic is ~4× faster per token than eight.
  5. Size the KV grant and max-num-seqs together. They trade against each other at a fixed footprint.
  6. Budget host RAM. ~5 GB per engine before any offloaded working set.
  7. Judge capacity by scheduler queue wait. Neither SM-active nor delivered/offered over a fixed request count is reliable.

7 · LimitationsWhat this does not establish

  • Mostly single runs. Repeated: the N=4 collapse (4 stock runs), N=8 resident (4 stock, 3 capped), 0.5B offload N=3 (2). Other points are n=1; curves are smooth and monotone but carry no error bars.
  • Capacity windows are short (300 requests, 10–20 s at the highest rates) and cover decode-only · fits only. The 0.5B limit was not located; the 3B limit is the sequence cap, not the GPU.
  • Mixed thread settings. The 0.5B resident curve at N=1–6 used stock threads; capped runs exist for N=8 and all offload points.
  • Unidentified: which code spins; which resource 3B reloads queue on; the cause of two client-side broken-pipe failures (1 of 2,400 requests in two of seven N=8 runs, no engine error).
  • Per-GPU telemetry. DCGM counters blend all N engines; per-model claims rest on client latencies and per-engine metrics.
  • Not measured: no-MPS scaling with N, priority or gating between models, mixed model sizes, a prefill-only configuration, other hardware or workload shapes.
