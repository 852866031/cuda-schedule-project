GPU 共享实验 · 第七个研究

一张 GPU 放 N 个模型，会发生什么

我们想在同一张显卡上同时运行很多个模型。这份报告用尽量少的术语讲清楚三件事：我们做了什么实验，模型变多之后先出问题的是什么，以及如果你也要这么做该注意什么。

8 个小模型同时跑在一张 GPU 上，每个都能完整服务自己的请求，没有请求超时或排队。
3.6×代价是变慢：8 个模型时，每个模型吐出一个字的时间是单独跑时的 3.6 倍。
4 个模型就能让系统崩溃，原因不在 GPU，在 CPU 的一个默认设置。改一个参数就好。

一句话结论：多个模型共用一张 GPU 是可行的。付出的主要是“每个字出得更慢”，能承受的总请求量比预想的大得多。最容易踩的坑在主机 CPU 上，而且很容易避开。

背景为什么这件事不简单

一个模型用不满一张 GPU 是常事：一张 32 GB 的显卡，放一个 1 GB 的小模型，大部分时间都闲着。很自然的想法是多放几个。问题在于，多个模型会同时争抢好几样东西，而且哪一样先不够用，事先并不知道。

三个概念读懂后面内容需要的全部背景

后面的结论都建立在三个概念上。每个只需要一段话。

1. 模型是一个字一个字往外吐的

模型回答问题分两步。先把你的问题整个读一遍，这一步叫 prefill。然后一个字（准确说是一个 token）一个字地生成回答，这一步叫解码。我们最关心的速度指标是“出一个字要多久”，后文记作每字耗时（英文缩写 TPOT），单位是毫秒。

2. 模型有“记忆”，记忆要占显存

模型读过的内容会存成一份中间结果，叫 KV 缓存。有了它，同一段开头（比如同一份长文档）再次出现时不用重读。KV 缓存放在显存里，很占地方。显存放不下时，可以把一部分挪到主机内存，用到时再搬回来，这叫溢出。

3. 一起算比分开算划算

同一个模型同时收到好几个请求时，可以把它们合成一批，一步同时为所有请求各出一个字。这叫批处理。对小模型来说，一批算 2 个请求和算 8 个请求，花的时间几乎一样。记住这一点，它是后面最重要的一个结论的来源。

实验设计我们是怎么测的

机器有两张 RTX 5090 显卡（每张 32 GB 显存）、32 核 CPU 和 60 GB 内存。我们把 N 个一模一样的模型全部放在其中一张显卡上，然后让 N 一点点变大。每个模型都有自己的客户端，按固定速率发请求：每秒 2 个请求，每个请求带一段很长的开头（约 6000 个 token），生成 128 个 token 的回答。

每组模型都在两种“记忆压力”下各测一遍。区别只有一个：需要记住的内容是否放得进显存。

另外，所有模型地位平等，没有谁优先。GPU 上开了一个叫 MPS 的共享模式，它让多个程序可以真正同时使用 GPU，否则它们只能轮流用。之前的研究已经确认：不开 MPS，两个模型就会互相拖慢到 3 倍以上。

发现一模型越多，每个字出得越慢，但都跟得上

先看最干净的情况：记忆放得下。模型从 1 个加到 8 个，每个模型都完整处理了自己的请求，没有请求超时或排队。8 个小模型合起来每秒输出约 2000 个 token。

发现二真正让系统崩掉的，是 CPU 上的一个默认设置

在“记忆放不下”的情况下，3 个小模型一切正常。加到第 4 个，系统突然崩溃：每个模型 300 个请求里约有 130 个超时，总输出掉到应有的 18%。

奇怪的是，崩溃时 GPU 几乎是闲着的，主机 CPU 却被占到 93% 以上。GPU 没事可做，是因为数据卡在了 CPU 这一侧。

原因：线程比 CPU 核多太多

每个模型的程序里都有一组负责 CPU 计算的工作线程。默认情况下，程序会按“整台机器都归我用”来开线程，这台 32 核的机器上每个模型开了约 135 个。只跑一个模型时没问题。跑 4 个模型，就是 540 个线程抢 32 个核。

更糟的是，这些线程在等同伴时不会让出 CPU，而是原地“空转”。于是真正要干活的线程抢不到核，搬运记忆越来越慢，积压越来越多，最后所有核都在空转，系统卡死。记忆放不下时每个请求都要 CPU 搬运数据，所以最先中招。

我们怎么确认是它

排除了其他嫌疑

负责存记忆的后台程序几乎不占 CPU。一个看起来可疑的缓冲区报警，在正常运行时也大量出现；把缓冲区加大一倍也没用。

只改一个变量

其他完全不变，只限制线程数：崩溃消失，0 个请求失败。线程数设成 2、4、8，结果都一样。

看到了“空转”本身

逐个线程采样：崩溃瞬间约 27 个线程占满 32 核，全部在空转，被系统强行打断的次数涨了 42 倍。

换模型也一样

中号模型在 4 个、记忆放不下、不加限制时同样崩溃：1200 个请求里 180 个超时。

不只是“记忆放不下”时才出事。8 个小模型、记忆放得下时，默认设置下 4 次运行里有 2 次出现了十几秒的同类卡顿。它会自己恢复，平均速度看不出问题，但最慢的那批请求从 0.9 秒拖到了最长 8.4 秒。加了限制后跑了 3 次，一次都没出现。

限制线程没有代价。单个模型时加不加限制，各项结果相差不到 3%。

发现三能承受的请求量，比“每秒 2 个”大得多

前面都是在每个模型每秒 2 个请求下测的。在这个负载下所有模型都跟得上，所以只能看出“慢了多少”，看不出“离撑不住还有多远”。于是我们固定模型数量，不断加大每个模型的请求速率，直到请求开始排队。

原因就是前面说的批处理：请求变多时，模型只是把更多请求塞进同一步一起算，而每一步的耗时涨得很慢。所以发现一里“8 个模型慢了 3.6 倍”说的是速度，不是容量。

这个上限是我们自己做的取舍。为了让每个中号模型多留些显存放记忆，我们把“同时处理的请求数”从 64 调到了 16。多出来的记忆空间，是拿并发能力换的。这两个设置要放在一起考虑。

建议如果你也要在一张 GPU 上放多个模型

  1. 先限制每个模型的 CPU 线程数。设 OMP_NUM_THREADS，取值不超过“CPU 核数 ÷ 模型数”。这一条没有代价，却能避免最严重的故障。
  2. 打开 MPS。否则多个模型只能轮流使用 GPU。
  3. 预期每个字会变慢，而不是服务不过来。小模型 8 个时慢 3.6 倍，中号模型 4 个时慢 2.5 倍。能不能接受，取决于你的延迟要求。
  4. 为了隔离才拆成多个模型。同一个模型想扛更多流量，交给一个实例做批处理更快。
  5. 尽量让记忆留在显存里。放不下时，小模型问题不大，大一点的模型会明显排队。
  6. 算内存，不只算显存。每个模型的程序自己要占约 5 GB 主机内存，溢出的记忆还要另算。
  7. “留给记忆的显存”和“同时处理的请求数”一起定。它们此消彼长。
  8. 判断是否撑得住，看请求有没有排队。GPU 的“忙碌程度”读数会误导人：负载翻倍时它甚至可能下降。

局限这次没有回答的问题

  • 小模型的容量极限在哪里。我们加到了基准的 8–16 倍都没有排队，没有继续往上找。高负载下的每次测量只有十几秒，还不能说明能长时间稳定。
  • 大多数数据点只跑了一次。崩溃（4 次）和 8 个模型的卡顿（共 7 次）是重复验证过的。
  • 中号模型搬运记忆时，具体卡在 GPU 的哪个环节，还没有分清。
  • 是哪一段代码在空转，没有定位到。机器没有相应的调试权限，只能确认空转这个行为。
  • 没有测的情况：大小模型混着放、模型之间分优先级、只做 prefill 的服务方式、不开 MPS 时随模型数的变化。
  • 8 个小模型的 7 次运行里，有 2 次各出现 1 个请求（每次共 2400 个）因客户端连接中断而失败，模型一侧没有报错，原因没有查。
  • 只在这一台机器、一种请求形态上测过。

名词表文中出现的术语

token
模型处理文字的基本单位，大致相当于一个字或半个词。
每字耗时（TPOT）
生成相邻两个 token 之间的时间。越小越快。
首字时间（TTFT）
从发出请求到第一个 token 出来的时间。
prefill / 解码
先整段读入问题（prefill），再逐个 token 生成回答（解码）。
KV 缓存
模型读过内容后留下的中间结果，文中称“记忆”。占显存，可以复用。
溢出（offload）
显存放不下的 KV 缓存挪到主机内存，用到时再搬回显存。
批处理
同一个模型把多个请求合在一步里一起计算。
MPS
NVIDIA 的多进程共享模式，让多个程序真正同时使用一张 GPU。
线程
程序里并行干活的执行单元。线程数远多于 CPU 核数时会互相妨碍。
QPS
每秒请求数。本文基准是每个模型每秒 2 个。
